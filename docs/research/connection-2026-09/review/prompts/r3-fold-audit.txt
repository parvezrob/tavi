## 0. What "A+" means, in numbers we can actually measure

No app can promise 99.99 % of wall-clock time: the phone's radio and ISP sit outside every SLA (Cloudflare, AWS and Ably all exclude them). What Tavi can promise is behaviour under a stated condition, measured as two separate things, because "attempts that succeed" and "minutes a live session is broken" have different denominators and cannot be converted into each other.

| SLI | Definition | Target | Condition |
|---|---|---|---|
| **Attempt success** | Opening the app, or a terminal, ends with an *authenticated* connection and the *current* state rendered and usable (not merely a socket) within 5 s | ≥ 99.9 % of attempts at launch, ≥ 99.99 % after phase 5 | phone has working internet to at least one relay provider; host process up with working uplink |
| **Session interruption** | Time between the last authenticated progress from the host and the next, whenever that gap exceeds 2 s, summed over foreground session time. Measured from the last *proof of liveness*, so a frozen screen still labelled Live counts from the moment it froze (with the detection uncertainty stated) | **owner's choice, §8**: 99.9 % (≈ 6 min per 100 session-hours) as the launch gate, 99.99 % (36 s per 100 session-hours) as the "A+" gate | same |
| **Recovery after a detected fault** | Fault detected → live screen back | ≤ 1 s (P95) when an alternate route is *warm* (definition in Layer 2.7); ≤ 3 s (P95) when a new outer connection must be built on the surviving interface; both measured Dhaka-LTE→Virginia as well as Dhaka→home Mac | same |
| **Detection of a silent stall** | Peer stops answering with no error → fault detected | ≤ 10 s (absolute, from the last authenticated response) while a terminal is on screen | — |
| **Explicit close or relay eviction on an unchanged network** | Socket closed by peer, DO deploy | ≤ 1 s to live screen (P95) | alternate warm |
| **Interface loss** (Wi-Fi gone, LTE only) | Both warm sockets die together; a new outer connection is built on LTE | ≤ 3 s to live screen (P95) from the path-change event | — |
| **Screen** | Never blank. The last frame stays, marked stale, with the status over it, until a fresh repaint arrives | invariant | — |
| **Input** | Ordered, duplicate-free delivery across route changes *within one live input session*; when that session's state is lost, the app says delivery is uncertain and asks (today's behaviour), it never replays on its own | invariant | — |
| **Honesty** | Status distinguishes: phone offline · internet reachable but computer unreachable through route X · computer reached but not answering · unknown | invariant | — |

Every latency target is a P95 over the release's measured population; the unit of an attempt is one user opening one screen once. How it is measured: opt-in client counters with the attempt outcome and the route (failed attempts reported when the phone is next online), the chaos harness from #111 extended with route kills, and physical LTE runs. These establish the SLIs per release; a fleet-wide four-nines claim needs fleet-wide data, which does not exist before there is a fleet. Until then the number is a design target, not a marketing claim.

A single relay vendor cannot carry the target: Cloudflare had a ~6 h global outage on 2025-11-18 and a 6 h partial one on 2026-02-20 (about a quarter of BYOIP prefixes, Spectrum down); Fly had a 7 h global one in 2024-10. **Two independently operated routes to every host, and a session that survives moving between them, is the whole design.** Independence is engineered, not assumed: separate providers, separate DNS zones for the two relay endpoints, separate deploy credentials, staggered releases, relay endpoints cached on both peers at pairing **as hostname plus last-known addresses** (TLS still verifies the hostname, so a cached address is safe to dial when DNS is down), the two relay zones on two different DNS operators, and endpoint changes published to phones as host-signed lists with a 90-day overlap so a phone that was offline through a migration still has a valid set.

## 1. Why this morning was structural

- The stall is a **known, open Tailscale iOS bug class**: tailscale#19504 (opened 2026-04, active 2026-09-06, "MagicSock ReceiveIPv4 goroutine stops, data plane dies while control plane stays up"), #18889, #15271 (status when failing: `UDP = No`, our `udp=false`), #17967, #15776 (clients do not detect DERP loss; keepalives are one-way). The reporters run SSH, tmux and mosh from phones: "every 2–3 minutes", "an interactive terminal reliably exposes it; toggling Tailscale restores connectivity immediately", "fails again within 15 min". A third-party analysis (2026-08-21) gives a mechanism (the receive closure dies on ENOTCONN during a socket rebind and nothing restarts it). Our evidence is consistent with this class; it does not prove that exact mechanism, and the incident report leaves the DERP question open.
- **Tavi can detect failed reachability; it cannot repair another app's VPN.** No public API restarts another vendor's extension.
- **App Review 4.2.3(i)**: "Your app should work on its own without requiring installation of another app to function." A Tailscale-only transport is a review risk on top of a reliability one.
- Customers run agents on rented VPSes (public IP, Linux) as often as on a Mac behind home NAT. Both must be first-class; today Tailscale is required for both.

What the field does (`01-product-survey.md`): **every coding-agent product** (Claude Code Remote Control, Codex Remote, Cursor self-hosted machines, VS Code Tunnels, Happy Coder, Omnara) uses one long-lived outbound connection to a vendor relay and none hole-punches; only Happy Coder and VS Code Tunnels keep end-to-end encryption. Remote-desktop products hole-punch because video needs UDP throughput, and the ones with no relay (Parsec on CGNAT, Moonlight, Screens) have the worst "works at home, fails remotely" reputations; RustDesk merged WebRTC on 2026-09-05 for exactly that reason. Roaming without re-authentication exists in four designs: Mosh, WireGuard, QUIC, Chrome Remote Desktop's ICE restart. Heartbeats converge on 3–5 s. Control planes are the outages customers see as "your machine is offline" (Jump 24 h, Happy ~20 h, Funnel silently dead while reporting healthy). On iOS every terminal vendor keeps the process alive with Location "Always" or accepts 20–30 s of background; Blink serializes mosh's state and rehydrates it.

**Why relay-first and not iroh-first.** The strongest case for iroh: it already has authenticated encryption, hole punching, relay fallback and multipath migration, and the alternative is an unwritten transport system. The case against betting on it today: 1.0 is three months old, its Node binding lagged 13 months before 1.0, its iOS build has an unverified `CoreWLAN` link and unmeasured size, its hole-punch rate on LTE CGNAT is unpublished, and its free relays are rate-limited with no guarantees. So phase 1 is a **comparative bake-off**, not a gate that prejudges the answer: inner-TLS-through-a-pipe and iroh are both built to the same small workload and run through the same failure matrix, and phase 1 ends with an explicit selection. If iroh wins it becomes the principal transport (its relays self-hosted on two providers) and Layer 4 shrinks to its relay; if the pipe wins, iroh may still return later as a `p2p` route. Nothing above the transport changes either way. A terminal at 1–5 KB/s does not need P2P for bandwidth; it needs a relay close to both ends, fast detection, and a session that survives the switch.

**Why end-to-end TLS inside the relay, not a new Noise protocol.** The app's whole surface is HTTP + WebSockets. If the relay is a dumb byte pipe and the *host itself* terminates TLS 1.3 with a key the phone pinned at pairing, then every existing route (`/api/*`, both WebSockets, uploads, the preview door) works unchanged through the relay, the bearer credential stays inside the encrypted channel, revocation keeps working exactly as today, and the relay operator sees ciphertext. This is the Tailscale Funnel model, which the survey found to be the only hosted design where the provider cannot read traffic. A Noise design would have to re-carry all of that surface itself, and its 65,535-byte record limit is already smaller than one Tavi frame. Noise stays as the fallback if the TLS-through-pipe adapter fails its spike.

## 4. The design: three layers, several routes

### Layer 1 — Identity and trust (prerequisite for everything else)
1. **Host key pair.** The host generates an Ed25519 (or P-256) key pair; the existing random identity becomes the seed so the *displayed fingerprint stays the same* where possible, or a versioned identity file replaces it. The host serves TLS 1.3 itself with a self-signed certificate for that key. The fingerprint shown on both screens is derived from the public key.
2. **Pairing v2** (`tavi://pair?v=2&…`): the QR carries the full host public key, the host's relay endpoints for both providers, and the single-use secret. The phone verifies the fingerprint it shows against that key and *pins the key*. The pairing exchange happens inside a TLS session pinned to it (over Tailscale, LAN, direct or relay). The phone also generates a device key pair; the host records its public key beside the bearer credential.
3. **Admission to the relay, without a deadlock.** A host registers by signing a fresh relay challenge with its key (proof of possession). With its registration the host publishes the **public keys of its paired devices** (identity metadata only, no content) and updates that list on every registry change. A phone is admitted to a host's channel by signing the relay's challenge with its **device private key**, checked against that list. So a phone that was offline for a month is admitted exactly like one that connected yesterday: there is nothing to expire and nothing to renew. **First pairing** is the one case with no device key on the list: `tavi pair` registers the single-use pairing secret's hash with the relay for its 5-minute life, and a phone presenting that secret is admitted to *one* channel that the host restricts to the pairing endpoint until the exchange completes inside pinned TLS. Bounded: five outstanding pairings per host, one channel each, five minutes.
4. **Revocation and rotation.** The host's device registry stays the single authority. Today's 2 s recheck covers the terminal and events sockets; it is extended to **every** inner session (ordinary requests carry the credential already; standby connections are rechecked on the same clock; preview tickets are bound to the device that minted them and die with its revocation, which `PreviewRegistry.admit()` does not do today; streaming and HMR connections through the door are terminated with the ticket). Revocation also pushes the updated device-key list to both relays, so relay admission for that device ends within one registration update (seconds, stated as a delay, not "immediate"); the host's own check is what is authoritative and it needs no relay cooperation. Device-key replacement (a phone restored from backup, a lost phone) is a re-pair; the old key is revoked. Host-key rotation is a re-pair of every phone, announced through the existing authenticated route with an overlap window; a host-key mismatch stops automatic connection and never falls back to a weaker route. Legacy bearer-only pairs are retired after the migration in 1.5 completes.
5. **Migration.** Existing phones learn the host public key and generate their device key over their current authenticated Tailscale connection once, then behave as v2 pairs. Never from a relay.

### Layer 2 — Session (what makes route changes invisible)
1. **Transport ≠ attachment.** A route is *established* (outer connection, inner pinned TLS, bearer check, HTTP host probe) without touching any terminal. Terminal ownership is a separate, explicit **activation** on exactly one route. Three identifiers are kept apart: the terminal's **ownership epoch** (changes on every takeover), the phone's **logical client session** (survives route changes), and the **route generation** (changes on every promotion). An activation names the ownership epoch it expects and is idempotent and queryable, so a lost acknowledgement is resolved by asking, and a *delayed* activation from an older route generation is rejected, never applied late. Late `ready`, input, resize, output and close callbacks from an older generation are dropped. A warm standby never claims or resizes a PTY. After **another device** takes over, this device does not reclaim automatically (it may have missed `superseded`); the user acts, as today.
2. **Input** within a live input session (device × terminal × ownership epoch): the phone numbers every input frame; *acceptance* means the host handed the bytes to the PTY (not that the application acted on them); the host acks the highest *contiguous* accepted sequence and rejects a resend whose bytes differ from what it accepted under that number. On route switch the phone resends only unacked frames and the host drops duplicates. Bounded queue. **Expiry never produces "not delivered"**: input that was sent but never acked is *delivery uncertain*; when the phone reconnects within the host's retention it reconciles against the host's ledger and learns which frames were accepted; when it cannot (host restarted, attachment replaced, ledger gone) it says so and asks, exactly as today. An expired unacked frame is resolved by fencing: the phone closes that input session and opens a new epoch, so no gap is ever skipped silently. The capability is negotiated, so an older host never sees a resend.
3. **Output** keeps v2 offsets and the epoch. Ring and retention are sized by measurement (4 MiB is ~14 min at 5 KiB/s; a burst is shorter) with a **host-wide budget** for retained PTYs and bytes, not a per-attachment number picked in a memo. Retention after detach: 10 min default, configurable, with a stated eviction order (oldest detached first). Output in the ring carries a **geometry version**; the existing 8 s hand-back to desktop geometry (`attachment.ts:188`) changes it, and a resume that would replay across a geometry change is answered with a fresh repaint instead.
4. **Kept frame.** The terminal surface never clears on a connection-state change. On a resume miss the existing herdr repaint is used, and the stale frame stays *as an overlay marked stale* until a **repaint boundary** has been processed by the renderer. The boundary is a heuristic and is named as one: at least one output frame after `ready` followed by 150 ms of quiet, measured per application in phase 0 and adjusted; a bare timeout with no output never clears the stale mark, it reports "still repainting". After renderer or process loss the phone always requests a fresh repaint; it never claims a byte resume from a picture. No new emulator is introduced. Why 07:03 blanked is found and fixed first.
5. **Events**: full snapshots, unchanged, plus a snapshot revision scoped to a **host incarnation id** (new on every host start) so an older snapshot arriving on a losing route cannot overwrite a newer one, and a restarted host's revision 1 is not rejected by a phone holding the old incarnation's 900. Losing subscriptions are fenced by route generation before a new incarnation is accepted.
6. **Liveness end to end.** Every liveness check is an authenticated challenge inside the TLS channel, never an outer WebSocket ping (Cloudflare answers those itself without touching the host). Terminal on screen: a challenge every 5 s, each with an **absolute 5 s deadline covering queueing, send completion and the response**; the first missed deadline marks the route suspect and starts promotion preparation; a route is dead when **10 s have passed since its last authenticated response**. The events stream keeps the slower cadence. Path events come from the **outer** transport (the loopback leg always looks healthy). Detection, promotion, replay and render are budgeted separately (§0).
7. **Route promotion.** All configured routes are dialled in parallel on connect; the first to *establish* wins; one alternate stays **warm**, which means: outer connection up, inner TLS handshake done, bearer verified, HTTP host probe answered, challenged on the same 5 s clock. A terminal WebSocket is *not* pre-opened on the standby (that would be an attachment); activation on promotion is one round trip. The active route is swapped on a dead verdict, a path change (`betterPath`/viability from the outer transport, make-before-break as Apple documents), or an explicit close. **Interface loss is a different case**: two warm sockets on the vanishing Wi-Fi die together, and the promotion is to a *new* outer connection built on LTE; that is the 3 s row in §0, not the 1 s row. Route loss closes the affected inner TLS connections; consumers reconnect (Layer 3).
8. **Suspension is normal.** The phone keeps a coherent checkpoint *while in the foreground* (epoch, acked offset, geometry, the frame the offset corresponds to); the background callback only flushes it. On foreground it shows the cached frame as stale immediately, reconnects asynchronously, and requests a repaint rather than claiming a byte resume if the checkpoint is incoherent. Persisted contents use complete file protection, are excluded from backup, expire, are deleted on unpair, and are shown only behind the app's existing access gate. Raw pending input is *not* persisted across suspension; unacked input at suspension is *delivery uncertain* on return, resolved by reconciliation as in 2.2. The app-switcher snapshot and a locked device show a redacted surface, not the terminal.
9. **Predictive echo is a later experiment, not a promise.** Today's local composer already gives immediate feedback for typed text. A Mosh-style overlay (predict printable keys, reveal per epoch on confirmation, never inside the authoritative emulator, disabled in alternate screen, bracketed paste, IME composition and after cursor/mode changes, confirmation markers bound to input sequence + output offset and sent even when there is no output) is measured per application before any number is promised. Coding-agent TUIs redraw arbitrarily; the Mosh figures are Mosh's workload.

### Layer 3 — Routes
| Route | For | Establishes | Notes |
|---|---|---|---|
| `direct` | VPS or any publicly reachable host | TLS to `host:port` pinned to the host key | no third party; dual-stack hostname or literal IP is fine (the app is tested on NAT64 and IPv6-only, App Review 2.5.5) |
| `relay-cf` | everyone | outer WebSocket to the Worker at a deterministic name derived from the host key → inner pinned TLS | DO name is deterministic from the host identity so every ingress finds the same object; the host registers (with proof of possession) **before** any object is created; placement is best-effort and measured, not assumed |
| `relay-vps` | everyone, and self-hosters (`TAVI_RELAY=wss://my.box`) | outer WebSocket to whichever of ≤ 4 relays the host is registered on → inner pinned TLS | rendezvous without a directory: the phone caches all relay endpoints (hostnames + last addresses) from pairing and tries them in parallel; only the one holding the host's registration answers; the host keeps a registration on **both providers** at all times, so failover needs no discovery. Registrations carry a generation, so a duplicate (host restarted, old socket lingering) is replaced deterministically; a host that moves region re-registers and the phone's parallel try finds it; endpoint-set changes are host-signed with 90-day overlap |
| `tailnet` | existing Tailscale users | pinned TLS to the host's TLS port on its tailnet address | optional "Tailscale mode"; ignored when it does not answer; Serve is no longer in the path; a stalled Tailscale exit node can also swallow relay traffic, which the status must be able to name |
| `p2p` (later) | everyone, if the iroh spike passes | iroh connection → inner pinned TLS or iroh's own keys | slots in as a route; nothing above changes |

On the phone the routes are implemented once, as a **local proxy** (HTTP CONNECT or SOCKS on loopback), not a bare port forward: `URLSession` uses it through its proxy configuration, `WKWebView` through `WKWebsiteDataStore` proxy configuration (iOS 17+), `NWConnection` through its proxy settings. Logical names are preserved, so the API and the preview keep **distinct origins** (`api.<hostid>.tavi.internal`, `preview.<hostid>.tavi.internal`, resolved by the proxy, never by DNS), SNI and `Host` are right, secure cookies and redirects work, and the host's certificate is verified **in each stack** against the pinned host key (URLSession delegate, `WKNavigationDelegate` challenge, `sec_protocol_options` verify block): three verifiers, one shared function, tested separately. Inner ALPN is HTTP/1.1 until HTTP/2 WebSockets are actually implemented. **TLS does not migrate**: when a route is lost the proxy closes the affected inner connections, consumers reconnect, and the *session layer* does the recovery; HTTP mutations (create agent, commit, upload) are never raced or replayed automatically: idempotency keys where the host supports them, "result unknown, check" otherwise. The `tailnet` route is also pinned inner TLS, to the host's TLS port on its tailnet address, so `tailscale serve` no longer terminates anything for the app. Feasibility of the proxy across all three stacks, including the preview's HTML, assets, redirects, secure cookies and HMR WebSocket, is spike 1(a). The spike is a standalone target; the product's support floor stays iOS 26.

### Layer 4 — The relay service (ours, small but not trivial)
- **Protocol**: host registers over one WebSocket per provider with a signed challenge and its device-key list; phones connect with a device-key possession proof (or a pairing secret, Layer 1.3); the relay allocates a **channel** per accepted inner stream and forwards opaque byte frames in order per channel with channel generations, framing limits, cancellation and teardown. Per-channel flow control and bounded bytes-in-flight; interactive channels are prioritised over bulk; **bulk transfers (uploads, previews) use a second outer connection** so TCP head-of-line blocking on the host leg cannot stall a terminal challenge, and phase 1 measures terminal latency and false failovers during a maximum upload. When the host leg drops, every channel is closed; the phone treats a relay-side close as *retry*, and only an authenticated inner message (revocation, takeover) as *permanent*. A dead host cannot send an inner close; the phone's challenge deadline is what detects it.
- **Admission before allocation**: pre-authentication rate limits per IP and per host id, handshake deadlines, per-host quotas for admitted phones; an unsolicited connection can never replace a registered host.
- **Hibernation**: authenticated roles, channel maps, generations **and flow-control state** are reconstructed from WebSocket attachments after a DO hibernates (attachments are small; anything that does not fit is re-negotiated with a channel reset); a deploy still terminates WebSockets, which the session layer absorbs as a reconnect with jitter; rollouts are provider by provider with the other provider verified healthy first; VPS relays drain before restart; mixed versions roll back cleanly.
- **No account database**: the host key is the identity; the only state is live registrations. That is still coordination; it is written down, not declared absent.
- **Deployments**: Cloudflare Workers + Durable Objects with WebSocket hibernation; the same forwarding core as a Node program on two or three VPSes (Hetzner or Fly regions chosen by where customers are; Bangladesh today means Singapore first).
- **Metadata**: the relay sees host identity, device public keys, phone and host IPs, timing and volume. Not content. The **metadata lifecycle** is written down as a release criterion: which fields the relay code and the providers' access logs hold, retention (target: relay code holds nothing past the connection; provider logs at their minimum), who can read them, deletion on unpair, and that telemetry is opt-in and separate. Truthful wording for the app and the privacy policy: *"Session content is encrypted between your phone and your computer. Relay operators can observe connection metadata."* A **no-managed-relay mode** (direct and/or Tailscale only, or a self-hosted relay) exists so the PRD's "no mandatory hosted relay" promise survives as a choice, and it is verified to make **no** contact with managed infrastructure from either peer (no registration, no probe, no telemetry); the PRD's default changes and says so.

## 6. Costs, risks, and what stays unsolved

- **Money**: Cloudflare Workers + DO at the modelled workload (2,000 concurrent sessions, 2 h/day) ≈ **$39/month** *if* hibernation removes idle duration; if timers or our socket handling defeat hibernation, duration alone could be ~$700/month. VPS relays: $30–100/month compute plus egress that depends heavily on region (India is 6× the US rate on Fly). Both figures model *sessions only*; the design adds always-on host registrations on both providers, warm standbys with challenges, several inner connections, previews and uploads. Phase 1(c) produces a reproducible model from host connection-hours, active and standby message counts, measured billable duration, both directions, regional egress and full-failover load, with compute, bandwidth and operations separated. Managed realtime services would be $1–9 k/month; ngrok's terms forbid redistributing its agent.
- **Operations from the first managed release** (not "before 10 k users"): a named on-call owner, external end-to-end probes on both providers, certificate-expiry and billing alarms, abuse response, runbooks, provider-by-provider rollouts, capacity for one provider carrying everything, and a reconnect-storm test.
- **App Review**: 4.2.3(i) is a real risk of the current design and this plan removes it. 4.2.7 (remote desktop clients) is **unresolved**: whether a rented VPS counts as a user-owned computer and whether agent supervision makes Tavi a "mirror of specific software" is Apple's call. Positioning: *"a general-purpose remote terminal for computers you control, including your own Mac and Linux servers you provision"*, with arbitrary shell use demonstrable beside the agent features, an isolated reviewer host, and the question raised with App Review early (#37). Wording does not change what ships.
- **Privacy**: the relay sees metadata; the PRD's "no mandatory hosted relay" becomes "relay by default, never mandatory". That reversal is the owner's decision to make explicitly.
- **Background**: background execution time after backgrounding is finite and not guaranteed by Apple (vendors measure 20–30 s on recent iOS); the app's sockets die then whatever the transport, and that is true today with the VPN too. Live Activities can show status, they do not keep a socket alive. Location "Always" is not acceptable for Tavi.
- **Not solved by any of this**: the host asleep or off; the host's own uplink down; a wedged herdr. Those are host-side problems with host-side answers (wake-on-LAN, VPS, the host watchdog).

## 8. Decisions the owner is asked to make

1. **The reversal.** Default route = a Tavi-operated relay (end-to-end encrypted, metadata visible to the operator), with a no-managed-relay mode kept. The PRD says "no mandatory hosted relay" today; this keeps it non-mandatory but makes it the default. Yes or no.
2. **The session target at launch.** 99.9 % foreground session availability (about 6 minutes of interruption per 100 session-hours) as the launch gate, with 99.99 % (36 seconds) as the target the following phases work toward; or hold the launch until 99.99 % is demonstrated.
3. **Phase 1 as a bake-off.** Both candidates get a week; the memo does not pre-select. Agree, or pick one now.
4. **Regions for the VPS relay.** Singapore first (Bangladesh), then one in Europe and one in the US; or different.
5. **Tailscale's place.** Optional "Tailscale mode" that pairing no longer requires; or drop it entirely once the relay ships.
