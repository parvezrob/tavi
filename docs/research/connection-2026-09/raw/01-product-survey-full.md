# How phone-to-machine-behind-NAT products actually connect

Facts below are from primary sources (vendor docs, engineering blogs, source code, GitHub issues). Anything derived rather than read is marked **(inferred)**.

---

## 1. Remote desktop class

### Parsec — BUD
Custom protocol "Better User Datagrams": UDP + **DTLS 1.2 via OpenSSL**, "reliability semantics like TCP, but with a highly tuned and custom congestion control algorithm" ([blog](https://parsec.app/blog/a-networking-protocol-built-for-the-lowest-latency-interactive-game-streaming-1fd5a03a6007), [technology](https://parsec.app/technology)). Backend TCP 443, STUN UDP 3478, P2P UDP 8000–8010. NAT traversal is **STUN + simultaneous UDP hole punching** coordinated over a WebSocket "Signal API," plus UPnP; claimed **97% NAT traversal success, 95% of users connect** (technology page). **No public relay** — "All connections traveling through Parsec are peer-to-peer. They never transit Parsec's infrastructure" ([security](https://parsec.app/security)). The only relay is the self-hosted High Performance Relay, Enterprise-licensed, which "acts as a phony STUN server." Both sides behind CGNAT simply fails. E2E: AES-128-GCM / DTLS, "we couldn't see what you're doing even if we wanted to." **No roaming**: error 12007 — "Parsec gives your internet 60 seconds to reconnect **on the same IP address**." Latency claim: 7 ms added on LAN. **No iOS client at all.** Why they built BUD: *"We tried several solutions, like WebRTC, plain UDP, and others, but nothing could achieve the reliability of TCP with the latency of UDP"*; WebSockets rejected for "NAT traversal and their TCP based congestion control."

### Jump Desktop — Fluid / Jump Connect
Fluid is **built on WebRTC** — "Jump Desktop Connect uses an open source, widely deployed technology called WebRTC [to] create connections behind NATs and firewalls" ([admin guide](https://support.jumpdesktop.com/hc/en-us/articles/360042490351)). Direct UDP 35384–35484; signaling TCP 443 to `neuron.jumpdesktop.com`; relay `turn.jumpdesktop.com` over UDP and TCP 80/443. NAT traversal is stock **ICE/STUN/TURN**. **Vendor-run global TURN, free, not subscription-gated** — "Jump Desktop runs many high performance relays across the globe and it will automatically pick a server closest to you." Self-hostable relay on Enterprise is literally **stock coturn in Docker**. E2E: "always encrypted end to end using STUN, DTLS, TLS, SRTP. Our relay servers can not decrypt." Fluid 2.0 added **forward error correction** and bandwidth estimation ([changelog](https://changelog.jumpdesktop.com/jump-desktop-with-fluid-2.0-1yMoBG)). Resumption: reconnect on lid-open and "transient networking problems," **no roaming claim** (inferred: re-establishment, not migration). No VPN. Complaints: MacRumors — "most of the time I am told my Macs are offline… Tailscale makes it much more reliable"; cellular-only failures on the vendor forum; a 24-hour 2023 outage caused by "a network partition within our message passing service cluster" — a **control-plane single point of failure**.

### Screens by Edovia — Screens Connect
VNC/RFB over TCP, optional SSH tunnel. **No hole punching at all** — Screens Connect does **inbound port mapping** via NAT-PMP and UPnP IGDv1 plus a dynamic-DNS-style directory ([supported routers](https://help.edovia.com/en/screens-connect-5/faq/supported-routers)). **No relay of any kind.** For CGNAT, Edovia's own doc tells you to use Tailscale ([CGNAT article](https://help.edovia.com/en/screens-connect-5/troubleshooting/cgn)). Encryption only if you enable SSH. No resumption (inferred: TCP RFB to a fixed endpoint). This is the "port-forwarding era" design, and its troubleshooting section is 17+ articles about port mapping failing.

### Moonlight / Sunshine
RTP over UDP with **Reed-Solomon FEC** (default 20%), control over **ENet** (reliable UDP), RTSP/HTTP over TCP. **No ICE, no hole punching** — the only STUN is `SimpleStun.c`, "extremely rudimentary STUN code simply for deriving the WAN IPv4 address." NAT is solved by **inbound port mapping** (UPnP/NAT-PMP/PCP via the Internet Hosting Tool). **No relay**; the documented fallback is an overlay VPN, with the warning that if Tailscale can't go direct, "you will not be able to stream." E2E since Sunshine 0.22 (AES-GCM), but `lan_encryption_mode` defaults to **off**. **No resumption**: Sunshine pins the UDP peer at session start, `ping_timeout` 10 s. On iOS, App Store Guideline 4.2.7a forces LAN-only pairing, so **an overlay VPN is effectively mandatory** ([issue #417](https://github.com/moonlight-stream/moonlight-ios/issues/417)). Best mobile bug for your purposes: [#669](https://github.com/moonlight-stream/moonlight-ios/issues/669) — on IPv6-only cellular (NAT64), `getaddrinfo()` on an IPv4 literal returns a synthesized IPv6 **outside the VPN's routes**, so RTSP leaves the tunnel while HTTP works.

### RustDesk
Custom protobuf over TCP/UDP; `hbbs` rendezvous (21115/21116/21118), `hbbr` relay (21117). **No STUN** — a homegrown two-port reflexive probe classifies NAT as symmetric or not ([`common.rs`](https://github.com/rustdesk/rustdesk/blob/master/src/common.rs)). **Symmetric NAT is not traversed, it is a relay trigger**: in `client.rs`, symmetric peers collapse the direct-connect race timeout to 1000 ms so relay TCP wins. Relay is **fully self-hostable**, geo-routed on Pro; public default is a **single Vultr host in New York**. Hard caps in `hbbr`: 128 Mb/s per connection, 1024 Mb/s total, 32 Mb/s throttle after 30 min above 66%. E2E confirmed NaCl: Ed25519-signed identity, Curve25519 `box_` key seal, XSalsa20-Poly1305 `secretbox` with sequence-number nonces — **but only if the server public key is configured**. Notably, **WebRTC/ICE was merged into master 2026-09-05** ([PR #15684](https://github.com/rustdesk/rustdesk/pull/15684)) with an explicit rationale: *"NAT combinations that classic punching cannot traverse still end on relay today… ICE covers a strictly larger connectivity set."* Roaming: reconnect only, and historically re-prompted for auth ([#3272](https://github.com/rustdesk/rustdesk/issues/3272)). Mobile bugs are NAT-shaped: [#15920](https://github.com/rustdesk/rustdesk/issues/15920) — UDP hole punching fails when TCP and UDP egress from different public IPs, i.e. CGNAT; [#14791](https://github.com/rustdesk/rustdesk/issues/14791) — cellular clients can't reach an IPv4-only server.

### AnyDesk
**TCP only on the WAN** (80/443/6568); the only UDP is LAN multicast discovery ([firewall doc](https://support.anydesk.com/docs/firewall)). AnyDesk **publishes nothing about NAT traversal** — no STUN, ICE, or punching anywhere in their docs; the 2018 guidance was "If AnyDesk cannot establish direct connections automatically you may set up a listening port manually in your firewall." Default is server-routed through `*.net.anydesk.com` (10 A records, OVH). E2E claimed regardless of route: TLS 1.3 + RSA-2048 + AES-256 (**no primary source for Salsa20** — that's third-party folklore). No resumption; the vendor's own remedy for drops is to disable direct connections. Self-host only on Ultimate.

### Chrome Remote Desktop
**WebRTC for everything** — "Chrome Remote Desktop uses WebRTC for all data transport" ([architecture doc](https://chromium.googlesource.com/chromium/src/+/main/remoting/docs/architecture.md)). Video via SRTP, control/input via **SCTP data channels over DTLS**, all bundled on one 5-tuple. P2P is **UDP-only** (`PORTALLOCATOR_DISABLE_TCP`); TCP survives only as TURN-over-TCP/TLS. Standard ICE; ICE config fetched from `remotedesktop-pa.googleapis.com`, refetched hourly. **Google runs TURN**, with a server-dictated `max_rate_kbps` bandwidth cap; not self-hostable. Crypto: SPAKE2 over Curve25519 from the PIN, and — the interesting part — **every SDP offer/answer is HMAC-SHA256-signed with the auth key**, so Google's own signaling can't swap DTLS fingerprints.

**CRD has the only code-level roaming spec of the whole survey.** On ICE disconnect it sets `want_ice_restart_` and starts a timer; `kCloseAfterDisconnectTimeout = base::Seconds(10)`, after which it closes with "ICE has not reconnected in 10s." `control.proto`: an ICE restart "can be used to re-establish a connection, **without needing to re-authenticate the user**." Asymmetry worth noting: `RequestIceRestart()` is `NOTIMPLEMENTED()` unless role is SERVER — **only the host can restart ICE; the phone can only ask and wait**. They also deliberately gather candidates on cellular: a code comment says they'd like `PORTALLOCATOR_DISABLE_COSTLY_NETWORKS` "but this is unreliable on iOS." **Why they migrated off their own protocol (Chromotocol):** CL 1584932 — *"connect via relay for the first time but subsequent connection will fail until we wait for ~5 minutes. This is a known issue to Chromotocol… while WebRTC doesn't seem to be affected, even when using it on mobile clients."* There is **no iOS app** — it's a PWA.

### TeamViewer
Proprietary protocol, UDP/TCP 5938 → TCP 443 → TCP 80 (last resort, and explicitly **"No automatic reconnection if the connection is lost"**). Outbound-only, no inbound ports. **The only published relay fraction in this entire survey**: *"a direct connection via UDP or TCP is established in 70 percent of all cases… The rest of the connections are routed through our highly redundant router network"* ([security statement](https://www.teamviewer.com/en-us/global/support/knowledge-base/teamviewer-remote/security/security-statement/)). Caveat: that sentence is verbatim identical in their 2014, 2017 and current texts, and the newest Security Overview PDF (v1.3, 2026) **drops the figure entirely** — treat it as a decade-old constant, not telemetry. Method never disclosed (inferred: master-brokered punching). Crypto: legacy RSA-4096 + AES-256; 15.73+ uses mutually authenticated **TLS 1.3** + AES-256-GCM with PFS. Notable mobile review: holding the connection open after backgrounding "destroys your battery… 100% down to 9% in a couple hours."

## 2. Remote terminal / coding-agent class

### Mosh — the reference design
UDP, **State Synchronization Protocol**, server ports 60001–60999. Each datagram is a **self-contained idempotent diff between a numbered source and target state**, so there is no replay cache and no ordering dependency ([paper §2.2](https://www.usenix.org/system/files/conference/atc12/atc12-final32.pdf)). Roaming is the key trick: *"Every time the server receives an authentic datagram from the client with a sequence number greater than any before, it sets the packet's source IP address and UDP port number as its new 'target.'"* — "roaming works in and out of NATs, even ones that may themselves be roaming." **Heartbeat is 3 seconds**, chosen for three jobs at once: learn the client's new address, warn the user, and **hold the NAT mapping open**. Crypto: **AES-128-OCB3**, key printed over the SSH session then SSH closes. Why not TCP: *"because it runs over TCP, SSH does not support roaming among IP addresses, or cope with intermittent connectivity while data is pending, and is almost unusable over marginal paths with non-trivial packet loss"*; on TCP reconnect schemes, *"it could take several minutes or longer for a TCP connection timeout to occur… Mosh differs in that its roaming is immediate and automatic."*

Published numbers: **Sprint EV-DO 3G — SSH median 503 ms → Mosh median 5 ms**; Verizon LTE with a competing download — SSH median 5.36 s → Mosh <0.005 s; 50% packet loss — SSH mean 16.8 s → Mosh mean 0.329 s. **70% of keystrokes displayed immediately, 0.9% mispredicted** and repaired within one RTT. Mosh does **no NAT traversal**: "If you had to forward TCP port 22 on a NAT for SSH, then you will have to forward UDP ports as well."

### Blink Shell
Embeds mosh + ssh in-process. **No NetworkExtension** — verified: the shipped entitlements contain no `com.apple.developer.networking.networkextension`, and a repo-wide search for `NEPacketTunnelProvider` returns zero hits. Blink is the one client that **engineered around iOS suspension rather than fighting it**, in three parts: (1) on backgrounding it takes `beginBackgroundTaskWithName:@"Suspend"` and schedules self-suspension at `MIN(backgroundTimeRemaining * 0.9, 5 minutes)`; (2) `SessionRegistry.suspend` serializes every session to disk with `NSKeyedArchiver`; (3) **they patched mosh-client to dump and reload its SSP state** — `MoshSession` sends the escape `\x1e\x1a`, stores the serialized blob, and on resume calls `mosh_main(..., encodedState, ...)`, reviving the same SSP session against the still-running `mosh-server` with no new SSH login ([MoshSession.m](https://github.com/blinksh/blink/blob/master/Sessions/MoshSession.m), [issue #59](https://github.com/blinksh/blink/issues/59)).

For plain SSH the only lifeline is `geo track`, which is Apple's sanctioned background-location lever tuned for battery — `desiredAccuracy = 100000` (100 km), `allowsBackgroundLocationUpdates = YES`, `pausesLocationUpdatesAutomatically = NO`. Even so, [#1122](https://github.com/blinksh/blink/issues/1122) has users reporting "the mosh connection has dropped 3 times as I was composing this response," and [#2177](https://github.com/blinksh/blink/issues/2177) (Dec 2025, iOS 26) reports a **blank shell on return from background** fixable only by force-quit. Open request [#2120](https://github.com/blinksh/blink/issues/2120) asks to replace location tracking with **Live Activities**. Blink Build reaches cloud VMs over **WireGuard**, driven over mosh.

### Termius
SSH/Mosh (clean-room reimplementation, licence-driven) with auto-reconnect since 8.1.0 — but that restores **tab scrollback**, not server state (inferred). No NAT traversal of any kind; ProxyJump host chains only. The most valuable thing they publish is a hard number: *"Recent versions stop background activity almost immediately, **usually within 20 to 30 seconds**. Older versions could allow it for 2 to 3 minutes"* ([FAQ](https://docs.termius.com/help-center/faq/how-can-i-keep-termius-sessions-alive-in-the-background-on-ios-ipados)). Their documented workarounds are location tracking, Split View, tmux, and **Live Activities** (shipped in 5.6.1).

### Prompt 3 (Panic)
SSH + Mosh + **Eternal Terminal**. Panic's own comparison: *"Eternal Terminal works entirely over TCP. This makes ET less optimal than Mosh when connecting over low-bandwidth or high-latency connections, but it's identical or better to mosh in all other areas."* Roaming claim is explicit — "move between networks, even going WiFi to mobile… and maintain the connection" — but **entirely delegated to a server daemon**; plain SSH gets nothing. Sharp limitation: jump hosts work **only for SSH and port forwarding**, so Mosh/ET and reaching a private host are mutually exclusive. Background survival is the same location trick, shipped as a named feature: **"Connection Keeper"**, requiring Location Access = Always. They disabled VPN On Demand by default because "it caused instability for some users."

### Tailscale SSH
WireGuard/UDP 41641, STUN 3478, **DERP relay over HTTPS/TCP 443**. NAT traversal is the most sophisticated in the survey: STUN, UPnP/NAT-PMP/PCP, and the **birthday-paradox hole punch** — 256 ports open on the hard side, random probing from the easy side: 174 probes → 50%, 2048 → 99.9%, "20 seconds in we're virtually guaranteed" ([blog](https://tailscale.com/blog/how-nat-traversal-works)). Tailscale estimates **direct connections over 90% of the time**. Two hard NATs remain near-hopeless: "to hit 99.9%… 170,000 probes… that's 28 minutes." DERP is E2E-blind ("it's impossible for a DERP server to decrypt your traffic"), 20+ regions, and **runs over TCP — which means head-of-line blocking**, which is why the Oct 2025 **Peer Relays** feature runs over UDP instead ([docs](https://tailscale.com/docs/features/peer-relay)).

Roaming works because the **inner** address never changes: WireGuard "will use the outer external source IP address for determining the endpoint… enabling peers to roam freely between different external IPs" — and the whitepaper **cites Mosh by name as the precedent**. Timers from `magicsock.go`: `heartbeatInterval = 3s` (the same number Mosh chose), `trustUDPAddrDuration = 6.5s`, `endpointsFreshEnoughDuration = 27s` ("UDP NAT mappings typically expire at 30 seconds"). Tailscale SSH sets TCP keepalive idle to **72 hours** inside netstack.

The cost is the phone side. iOS **requires the VPN NetworkExtension**, and Tailscale's own test file states the ceiling: *"On iOS the Network Extension has a **hard 50 MiB phys_footprint limit (jetsam)**… of which ~15 MiB is non-heap"* ([membudget_test.go](https://github.com/tailscale/tailscale/blob/main/tstest/membudget/membudget_test.go)). Consequences in-tree: wireguard-go queues forced to 64 on iOS, gVisor buffers left at defaults "as to not increase pressure towards the NetworkExtension memory limit," and port mapping historically disabled on iOS for binary size. Issue backlog matches: extension fails to start under load ([#19810](https://github.com/tailscale/tailscale/issues/19810)), extension crashes ([#2566](https://github.com/tailscale/tailscale/issues/2566)), overnight silent disconnects ([#8183](https://github.com/tailscale/tailscale/issues/8183)) — "Opening the app resets the connection and fixes it." **Critically: the tunnel surviving backgrounding only preserves L3 reachability. A third-party terminal app holding the socket is still suspended and still loses it.**

### Eternal Terminal
TCP 2022, three processes, **no NAT traversal** and it can't even tunnel itself over SSH ([#274](https://github.com/MisterTea/EternalTerminal/issues/274)). Resumption is the cleanest published: reconnect with the same client-id, then *"bidirectional **SequenceHeader** protobufs are exchanged which contain the last received sequence number for each side. Based on this, **CatchupBuffer** protobufs are swapped, containing the missing encrypted packets"* ([protocol.md](https://github.com/MisterTea/EternalTerminal/blob/master/docs/protocol.md)). Buffers: 64 MB each way. Keepalives 5 s client / 11 s server — dead link detected in 5–10 s and NAT state stays hot, at the cost of a radio wake every 5 s. Crypto: libsodium XSalsa20-Poly1305, key = the passkey handed over SSH, **no rekeying, no forward secrecy**. The classic mobile failure is documented in [PR #762](https://github.com/MisterTea/EternalTerminal/pull/762): laptop lid closes, the 4 MB disconnect buffer fills with pending output, `etterminal` exits, the reconnecting client gets `INVALID_KEY` — **session gone**. Fixed by raising the buffer to 64 MB plus pty backpressure.

### ttyd / GoTTY / wetty
All three are **WebSocket over TCP**: an IP change kills the TCP connection and the session with it. ttyd's `--ping-interval` defaults to 5 s and `--signal` defaults to **SIGHUP on disconnect** — the child is killed, not preserved. GoTTY is blunter: *"GoTTY starts a new process with the given command when a new client connects"*, so `--reconnect` reconnects the socket and starts a **new process**. In all three, persistence is tmux's job. Browser delivery adds an iOS-specific failure: WebKit [bug 308073](https://bugs.webkit.org/show_bug.cgi?id=308073) (filed Feb 2026, iOS 26.3, still open) — after 10 s backgrounded the socket closes with 1006 and then **every subsequent `new WebSocket()` hangs in CONNECTING permanently**, while `fetch()` to the same server returns 200; only a full page reload recovers.

### Happy Coder
Runs on the user's machine (`happy` wraps `claude`). Transport is **Socket.IO** (websocket + polling fallback) at `/v1/updates`, with RPC multiplexed over the same socket. **Purely outbound to a slopus-run relay; zero hole punching.** Self-hostable. **The only genuine E2E in the coding-agent class**, verified in source: TweetNaCl `secretbox` (XSalsa20-Poly1305) legacy plus **AES-256-GCM** with the DEK wrapped under an ephemeral `box_` keypair; QR pairing encodes `happy://terminal?<base64url(publicKey)>` and the phone seals the account secret to it ([encryption.md](https://github.com/slopus/happy/blob/main/docs/encryption.md)). Metadata is not encrypted (session IDs, device IDs, timestamps, push tokens), and voice plus stored vendor API keys are explicit carve-outs. Resumption design: *"Anything that must be recoverable after reconnect is an `update` event with a sequence number"*, a single per-user monotonic `seq`, and reconnect via **cursor refetch** rather than a socket-level replay buffer.

Its bug list is the most instructive in the survey because it is the closest analogue to Tavi. [#1229](https://github.com/slopus/happy/issues/1229): the daemon never reconnects with the lid closed because `shouldReconnect()` returns false if `isLidClosed() && !hasExternalDisplay()`, so it logs "Still not ready to reconnect" every 3 s forever. [#989](https://github.com/slopus/happy/issues/989): "Daemon socket silently dies — no liveness probe or reconnection." [#1308](https://github.com/slopus/happy/issues/1308): mobile **misses messages after backgrounding** because ordinary `new-message` updates are not pushed by design, and session-scoped CLI sockets are miscounted as "user present," suppressing the pushes that would have covered it. Plus a ~20-hour hosted-relay degradation ([#1682](https://github.com/slopus/happy/issues/1682)).

### Claude Code Remote Control
Agent runs **on the user's machine**. Transport, stated unusually plainly: *"Your local Claude Code session makes **outbound HTTPS requests only and never opens inbound ports**… it registers with the Anthropic API and polls for work. When you connect from another device, the server routes messages… **over a streaming connection**"* ([docs](https://code.claude.com/docs/en/remote-control)). No hole punching. **Not E2E, and they say why**: the transcript "is stored on Anthropic servers," and that storage is load-bearing — it "keeps the conversation in sync across your devices and **lets the session reconnect after a network drop**." ZDR orgs can't use it. Resumption is the best-documented anywhere: *"if your laptop sleeps or your network drops, Claude Code reconnects automatically… While the connection is rebuilding, Claude Code **queues messages, permission prompts, and status updates** and delivers them once the connection recovers."* Concrete budgets: server mode gives up after ~10 min offline, presence-heartbeat failures re-register for ~30 min, `--continue` revives sessions for ~4 hours. Documented limitation: forwarded dialogs other than permissions **expire after 5 minutes and take their no-action default**, and mobile pushes are delayed by iOS Focus modes.

### Codex, Cursor, Omnara, VS Code Tunnels, Codespaces
**Most of these never traverse NAT at all.** Codex cloud, Cursor's default Cloud Agents, and Codespaces run the agent in the vendor's cloud. Omnara has pivoted — the agent loop lives in *their* control plane and your machine is only a tool-execution environment: "**the machine does not own the agent**… Disconnecting a machine does not kill the agent" ([docs](https://docs.omnara.com/machines/overview)). Its daemon protocol is worth noting anyway: a typed offer/accept/ack envelope with idempotency keys and error codes like `idempotency_conflict` and `presence_replaced`, which is what makes reconnection safe.

The ones that do reach your machine all do it identically. **Codex Remote**: the ChatGPT desktop app hosts, reached through "a secure relay layer… without exposing them directly to the public internet"; QR pairing; **no resumption documented** — "If that computer sleeps, loses network access, or closes the app, remote access stops." **Cursor Self-Hosted Machines**: "`agent worker start` opens a **long-lived outbound HTTPS connection**… **Cursor never connects into your network**… No inbound ports, public IPs, or VPN tunnels are required" ([docs](https://cursor.com/docs/cloud-agent/self-hosted)). **VS Code Remote Tunnels**: WebSocket relay in Azure (subprotocol `tunnel-relay-client`), and uniquely, "**an SSH connection is created over the tunnel in order to provide end-to-end encryption**" — so the relay carries SSH ciphertext for VS Code sessions, while generic web port-forwarding does **not** get that ("TLS termination is done at service ingress… After TLS termination, header rewriting takes place"). Reconnection and SSH keep-alive are implemented **only in the C# and TypeScript SDKs**; Go, Java and Rust have none.

Worth flagging: Codex's DIY `app-server` path is the inverse of everything else — JSON-RPC over a **listening** WebSocket — and OpenAI's own guidance is *"If you need to reach a remote machine outside your current network, **use a VPN or mesh networking tool** instead of exposing the app server directly to the internet."*

## 3. Tunnel-as-a-service

**Cloudflare Tunnel.** `cloudflared` makes four outbound connections on port 7844 to two nearby data centers. `--protocol auto` prefers **QUIC**, falling back to http2 if UDP is blocked. Their stated reason for QUIC: *"TCP traffic sent over HTTP/2 is susceptible to Head of Line blocking"* and *"it is currently not possible to initiate communication from cloudflared's HTTP/2 server in an efficient way"* ([blog](https://blog.cloudflare.com/getting-cloudflare-tunnels-to-connect-to-the-cloudflare-network-with-quic/)). 348 cities; 95% of internet users within 50 ms. **Not E2E** — TLS terminates at the edge, unavoidably. Two WebSocket landmines: Cloudflare documents an **unnumbered idle timeout** ("Cloudflare will close a WebSocket connection when no data is transmitted in either direction for a period of time"; the widely-cited 100 s figure is **no longer in their docs**) and acknowledges that "when Cloudflare releases new code… we may restart servers, which terminates WebSockets connections." And [issue #1652](https://github.com/cloudflare/cloudflared/issues/1652), open since May 2026: on the default QUIC path the **`Upgrade: websocket` header is dropped** before reaching the origin; `--protocol=http2` restores it. Free, but the ToS now names Tunnel public hostnames for large-file traffic.

**ngrok.** Long-lived **TLS over TCP 443** to `connect.ngrok-agent.com`, with heartbeats, backoff reconnect, and four DNS fallbacks. **8 PoPs** (vs Cloudflare's 348 cities). Free endpoints have **no timeout** — "they can stay online indefinitely." E2E is available but paid: TLS endpoints can terminate at the agent or upstream, where "the ngrok cloud service can not see payload." Free tier: 1 GB/mo, 20k requests, 3 endpoints, browser interstitial on HTML.

**Tailscale Funnel.** The only hosted option where the provider **cannot read your traffic**: "The Tailscale server running on your device receives the encrypted request from the TCP proxy. It then **terminates the TLS connection** and passes the decrypted request to the local service" ([KB 1223](https://tailscale.com/kb/1223/funnel)). Ports **443, 8443, 10000 only**; reverse-proxy backends limited to `http://127.0.0.1`; bandwidth limits are "non-configurable" and **unpublished**. The reliability backlog is the densest in the survey, including [#21114](https://github.com/tailscale/tailscale/issues/21114) (Sep 2026, open): after a control-plane reconnect, **Funnel silently stopped serving while `tailscale funnel status` reported healthy** — required a manual `tailscaled` restart.

**Others.** **zrok/OpenZiti** claims real E2E (XChaCha20-Poly1305, SDK-to-SDK, "even a compromised OpenZiti router can't see the raw data") but a plain phone browser isn't an SDK endpoint, so the public frontend is a plaintext point (inferred); 5 GB/**day** free, self-hostable. **Microsoft dev tunnels**: still public preview, no SLA, WS(S) supported, **TLS terminated at ingress** by design, 5 GB/user/month. **frp**: the credible self-host choice — Apache-2.0, v0.71.0 (Aug 2026), transports `tcp|kcp|quic|websocket|wss`, TLS on by default since v0.50.0, heartbeat 30 s / timeout 90 s. **rathole**: faster and smaller, Noise Protocol support, but **last tagged release v0.5.0 in Oct 2023**. **bore**: no encryption at all, and [automatic client reconnection is still an open feature request](https://github.com/ekzhang/bore/issues/188). **localtunnel**: effectively abandoned, and its IP-based interstitial password is structurally broken for a phone on cellular ([#727](https://github.com/localtunnel/localtunnel/issues/727)). All self-hosted options trade the trust problem for a **latency problem**: one VPS, no anycast, full geographic RTT with nothing to absorb it.

## Patterns

What the products with the strongest mobile-reliability reputation have in common:

1. **The session lives on the server, and the client is a re-attaching viewport.** Mosh-server, `etterminal`, tmux, Anthropic's server-side transcript. Every product that survives a network change does so because the authoritative state is *not* in the phone's socket. Termius's "auto-reconnect" preserves tab scrollback, not server state — and that distinction is exactly where user complaints cluster.

2. **Session identity is decoupled from the 5-tuple.** Mosh rebinds on any authenticated datagram with a higher sequence number. WireGuard rebinds on the outer source IP (and its whitepaper cites Mosh as precedent). QUIC uses connection IDs. CRD restarts ICE without re-auth. Every product that *doesn't* do this — Parsec ("same IP address," 60 s), Sunshine (peer pinned, 10 s), plain WebSocket-over-TCP — drops the session on handover.

3. **Recovery is a sequence number plus a replay buffer, not a fresh connection.** Eternal Terminal's `SequenceHeader` + `CatchupBuffer` (64 MB), Happy's monotonic per-user `seq`, Anthropic's queue-and-deliver, Omnara's idempotent offer/ack. ET's PR #762 is the cautionary tale: a 4 MB buffer that overflows destroys the session as surely as no buffer at all.

4. **Heartbeats converge on ~3–5 seconds, and they do triple duty.** Mosh chose 3 s; Tailscale's magicsock independently chose 3 s; ET chose 5 s. All three cite the same constraint — **UDP NAT mappings expire around 30 seconds** — and the same three jobs: detect death fast, learn the new address, hold the mapping open.

5. **Nobody in the coding-agent class hole-punches; everybody in the remote-desktop class does.** All eight agent products use a persistent outbound connection to a vendor relay, and every one advertises "no inbound ports" as the security feature. The desktop products punch because they need UDP throughput for video. For a terminal, the bandwidth argument for P2P mostly evaporates.

6. **Relay is not the fallback of shame — it's the reliability floor.** TeamViewer's published 70/30 split, WebRTC's industry ~15–20% TURN rate, Tailscale's "over 90% direct," Parsec's 97% claim. The products with the *worst* reputations (Moonlight, Screens, Parsec-on-CGNAT) are precisely the ones with **no relay**, where a symmetric-NAT pair means the connection simply fails. RustDesk merged WebRTC in Sep 2026 for exactly this reason.

7. **The relay's ability to read traffic is what buys cross-device resumption — and only two products refuse the trade.** Anthropic says it outright: storing the plaintext transcript is *what makes* reconnection work. Happy Coder and Tailscale Funnel keep E2E; Happy pays for it with an unencrypted metadata surface and the buggiest reconnect story of its cohort, and Funnel pays with port restrictions and silent-death bugs.

8. **On iOS every vendor independently landed on Location "Always" — because it's the only documented lever that keeps the app process alive.** Blink's `geo track` (accuracy set to 100 km to save battery), Termius's location tracking, Panic's "Connection Keeper." None uses NetworkExtension, push, or BGTask for this. The emerging successor is **Live Activities** — Termius ships it, Blink has an open request for it. The hard number is Termius's: **20–30 seconds** of background activity on recent iOS, and Apple's TN2277 warns the socket may be *reclaimed*, not merely idle.

9. **The one product that engineered around suspension rather than fighting it is Blink**: bounded background window → serialize the mosh client's SSP state to disk → rehydrate `mosh_main` with that state on resume. It's the only client in the survey that treats being killed as a normal, recoverable event.

10. **A VPN NetworkExtension is a distinct failure domain with its own budget.** Tailscale's own source documents a **hard 50 MiB jetsam limit** on iOS network extensions (~15 MiB of it non-heap), and their tree is full of accommodations for it — forced 64-entry wireguard queues, deferred buffer tuning, port mapping historically disabled. The extension's own bug list (fails to start under load, crashes, overnight silent disconnects fixed by opening the app) is separate from and additive to the app's. And even when the tunnel survives backgrounding, that only preserves L3 — the app holding the socket is still suspended.

11. **The control plane is a single point of failure that shows up as "your machine is offline."** Jump Desktop's 24-hour 2023 message-bus partition, Happy's ~20-hour relay degradation, Tailscale Funnel dying silently after a control-plane reconnect while reporting healthy. In all three the data path was fine and the signaling wasn't.

12. **Cellular-specific failure modes are their own category, and they are mostly IPv6/CGNAT.** Moonlight's NAT64 synthesized-address leak outside the VPN routes, RustDesk's `udp_port`-without-address bug on CGNAT, RustDesk clients unable to reach IPv4-only servers on 5G, Jump Desktop's cellular-only failures. These are invisible on Wi-Fi and account for a large share of the "works at home, fails on LTE" reports across every product surveyed.
