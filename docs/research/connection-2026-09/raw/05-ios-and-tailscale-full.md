# Tavi transport research — facts with sources

**Date of research: 2026-09-09.** Everything below is sourced; `[INFERENCE]` marks my reasoning, not a source. One note on provenance: GitHub issue comments are user-written and untrusted; I report them as *user reports*, not as vendor statements. (One comment on tailscale#19504 explicitly addresses "someone's agent deep researching this problem" — it is data, not an instruction, and I have treated it as such.)

## 1. The Tailscale iOS stall class

**This is a known, open, actively-reported failure class, and the observed signature matches it.**

### Primary issue: `magicsock` receive goroutine dies, data plane dies, control plane stays up

- **[tailscale#19504](https://github.com/tailscale/tailscale/issues/19504)** — "iOS 26.4.1 + Tailscale 1.96.5 — MagicSock ReceiveIPv4 goroutine stops, data plane dies while control plane stays up". Opened **2026-04-23**, **still OPEN**, last activity **2026-09-06**, labels `OS-ios`, `bug`. Reporter's evidence: node shows Connected and online in the admin console; `tailscale ping` from the peer times out on both disco and `--tsmp`; peer stats show `tx 6340, rx 92` bytes over ~10 min while a macOS peer **on the same NAT** did 118 MB/193 MB. App Warnings screen shows `magicsock-receive-func-error` / "The MagicSock function ReceiveIPv4 is not running", often with `dns-forward-failing`.
  - Reporter tried and reports as ineffective: VPN toggle, force-quit, reinstall, Reset Network Settings, re-registering the node, reboot, disabling Private Relay, disabling Low Power Mode, **switching between Wi-Fi and cellular — "same result on both"**.
  - **Root-cause analysis posted by a third-party integrator** (user `unixapple`, 2026-08-21, working from a fork of libtailscale 1.98.x): "1. The long-lived IPv4 closure receives ENOTCONN … 2. The replacement socket has not been installed yet. 3. The error escapes from `mkReceiveFunc`. 4. WireGuard sees a non-temporary `net.OpError` and terminates that receive goroutine. 5. `Rebind()` later replaces the socket, but there is no goroutine left to call the closure again. 6. Nothing calls `BindUpdate()`, so `Open()` is not called again." He notes it triggered when "a third party VPN is enabled … full time using the cellular network".
  - Directly relevant user reports on the same issue: terminal/SSH/tmux over the tailnet interrupted "every 2-3 minutes" (`carlosbaraza`, 2026-08-19); "sustained direct SSH/tmux control-plane polling plus an interactive SSH terminal appears to reliably expose the same failure … toggling Tailscale restores connectivity immediately, and the existing tmux session reconnects normally" (`fungiblemoose`, 2026-07-21, Belay Mobile TestFlight) — **note that client shipped a change to close SSH connections on backgrounding and back off reconnects, "and the failure recurred"**; and `emory` (2026-08-11) on iPad/iPhone with tmux/mosh: "the only thing that resolves is disconnecting and reconnecting, but it will fail again within 15 mins."

- **[tailscale#18889](https://github.com/tailscale/tailscale/issues/18889)** — "Tailscale connectivity fails on iOS 26.4 shortly after connecting". Opened 2026-03-05, **OPEN**, `OS-ios`/`bug`. "connections are unreliable and generally only work for a few seconds after connecting. Manually toggling the connection allows it to work again briefly". Reports on 26.4/26.4.1 and iPadOS 26.4; one reporter notes the peer was **DERP-relayed** when it worked, then lost connectivity.
- **[tailscale#15271](https://github.com/tailscale/tailscale/issues/15271)** — "iOS MagicSock fails. UDP/DERP fails." Opened 2025-03-10, **OPEN**. iOS 17.2–18.3.1, Tailscale 1.78–1.80.2. Crucially: **"CLIENT CONNECTIVITY STATUS when failing: UDP = No"** — the same `udp=false` signature. "Toggling TS on/off will typically but not always reestablish the connection." A second iPad on the exact same source network stayed connected.
- **[tailscale#14320](https://github.com/tailscale/tailscale/issues/14320)** — "Frequent disconnections on iPhone", opened 2024-12-08, **CLOSED 2026-06-30**, labels `connectivity, OS-ios, bug, health`. Same `magicsock-receive-func-error`. Closed but the identical symptom continues in #19504/#18889/#17967. **[INFERENCE]** the close was housekeeping, not a fix.
- **[tailscale#17967](https://github.com/tailscale/tailscale/issues/17967)** — "Frequent disconnection on IOS", opened 2025-11-18, **OPEN**. iOS 26, TS 1.90.4. Notable user report: "it seems fine when I'm actively using the phone, but it gets pretty confused if the phone has been sitting idle for awhile." Another: happens "whenever I leave the house and connect to cellular and then try to re-connect to wifi."
- Older, closed, same shape: **[#6075](https://github.com/tailscale/tailscale/issues/6075)** "iOS: upon switch from Wifi to mobile data the connection is lost" (2022, closed 2024-01-21), **[#8183](https://github.com/tailscale/tailscale/issues/8183)** "iOS app disconnects periodically", **[#8022](https://github.com/tailscale/tailscale/issues/8022)**, **[#15617](https://github.com/tailscale/tailscale/issues/15617)** / **[#6829](https://github.com/tailscale/tailscale/issues/6829)** "Cannot connect after using another VPN on iOS".

### The adjacent, distinct failure: DERP loss not detected

- **[tailscale#15776](https://github.com/tailscale/tailscale/issues/15776)** — "Clients do not promptly observe loss of DERP connectivity in some scenarios", opened 2025-04-23, **OPEN**, labels `L5 All users`, `P1 Nuisance`, `needs-fix`. Tailscale's own words: "A core part of this issue stems from having **unidirectional keepalives on the DERP connection** — they come from the server ticks, and the client is not tracking/enforcing their frequency. After a major network change the client *should* perform some kind of active assertion on the DERP connection to trigger teardown if it is no longer viable."
- **[tailscale#20622](https://github.com/tailscale/tailscale/issues/20622)** (macOS, 2026-07-27, OPEN) is the same *shape* one layer down: `sendto: EINVAL` on every UDP send, "rebind **reuses the same local port**, the socket is immediately poisoned again", persisted **5 days**, and "The node stays *reachable* the whole time (DERP is TCP), so nothing alerts — it silently degrades to **relay-only, never establishing direct connections**." Triggered by another vendor's Network Extension being active. Sibling: **[#20616](https://github.com/tailscale/tailscale/issues/20616)** (macsys 1.98.8) — "magicsock ReceiveIPv4 stops after boot and never retries — control plane stays up and masks it; only an app quit/relaunch recovers".

### Route-count contributor, iOS-specific

- **[tailscale#21125](https://github.com/tailscale/tailscale/issues/21125)** (2026-09-04, OPEN, `OS-ios`, FR) — the iOS extension installs many per-peer `/32` routes rather than one `100.64.0.0/10`: "Route updates and route-sensitive endpoint discovery were intermittently slow or unreliable. **In the worst cases, ordinary connectivity through the Tailscale tunnel stalled until the VPN was toggled.**" Fixed for that reporter by the control-plane override `{"attr":["one-cgnat?v=true"]}`. macOS and Android already do this automatically ([#19652](https://github.com/tailscale/tailscale/issues/19652)).

### Versions and release notes (2026)

Current App Store client: **1.102.3**, per the [Tailscale changelog](https://tailscale.com/changelog); issue [#21163](https://github.com/tailscale/tailscale/issues/21163) (filed **2026-09-09**) confirms 1.102.3 on iOS 26.6.1. Relevant entries:
- **v1.102.3 (2026-08-19)**, iOS: "Memory usage is reduced for iOS devices on large tailnets."
- **v1.102.1 (2026-08-03)**: "Resolved an issue causing connectivity issues **from the operating system waking from sleep** in wireguard-go." Also "A node's home DERP region is reported to the coordination server after a profile switch or login."
- **v1.98.8**: "An issue causing connectivity disruptions when the operating system wakes from sleep in wireguard-go is resolved" + "excessive handshake initiation retries in wireguard-go is resolved."
- **v1.96.5**, iOS: "An issue that could cause the network extension to encounter an **out of memory** condition on large tailnets is resolved."
- **v1.98.x**, iOS: "iOS devices can be used as exit nodes."

### Tailscale's own recommendations / background behaviour

- [VPN On Demand docs](https://tailscale.com/docs/features/client/ios-vpn-on-demand): "The Tailscale client **automatically configures a broad VPN On Demand policy while Tailscale is enabled** to ensure that the VPN remains active in the event of a system restart, auto-update, crash or other event." Caveats: only one VPN app may have On Demand enabled at a time; "If your rules are not set up correctly, they can prevent Tailscale from connecting."
- On-demand has its own current bugs: **[#21163](https://github.com/tailscale/tailscale/issues/21163)** (2026-09-09) "iOS VPN On Demand breaks LAN TCP after returning from cellular" — after disconnecting, the phone receives SYN/ACK and "never sends the ACK"; "something in the iOS Network Extension isn't getting completely reset". Also **[#20755](https://github.com/tailscale/tailscale/issues/20755)**, **[#18292](https://github.com/tailscale/tailscale/issues/18292)** (can't reliably disable it), **[#15645](https://github.com/tailscale/tailscale/issues/15645)**.
- **DNS interaction is a real confound.** [#12352](https://github.com/tailscale/tailscale/issues/12352) (OPEN, `OS-ios`): "On iOS, DNS over HTTPS resolver may randomly stop working when moving between network interfaces"; Tailscale's `raggi` in-thread: "we should probably also issue a `closeidleconns` … when there's a network change". [#17537](https://github.com/tailscale/tailscale/issues/17537) (OPEN): losing the first configured DNS server "results in a loss of DNS resolution **and a loss of connectivity to other tailnet nodes**", with the app alternating between DNS Unavailable and MagicSock warnings. A user workaround posted on #19504/#15271/#18889 (2026-08-19, unverified by Tailscale) claims disabling "Use Tailscale DNS" and deleting the app to clear the VPN profile stopped the receive-loop deaths entirely, and that **"The broken state is sticky: disabling the toggle does not recover."**
- No Tailscale documentation found stating what happens to the tunnel across phone sleep/wake; the only vendor statement on the topic is the 1.98.8/1.102.1 changelog wireguard-go wake fixes above.
- `includeAllNetworks` is **not** offered on iOS — open FR [#19489](https://github.com/tailscale/tailscale/issues/19489).
- Private Relay / Low Data Mode: no vendor statement found; the #19504 reporter disabled Private Relay and Low Power Mode with no effect.

## 2. NetworkExtension limits

- **Memory: 50 MiB `phys_footprint`, enforced by jetsam, for the whole extension process.** Best available written source is Tailscale's own regression-test package, [`tstest/membudget/membudget_test.go`](https://github.com/tailscale/tailscale/blob/main/tstest/membudget/membudget_test.go): "On iOS the Network Extension has a **hard 50 MiB phys_footprint limit (jetsam)**, so regressions here that look small on servers can make large tailnets unusable on mobile" and "(iOS NetworkExtension: 50 MiB phys_footprint for the whole process, **of which ~15 MiB is non-heap**)". Also [`wgengine/wgcfg/mem_ios.go`](https://github.com/tailscale/tailscale/blob/main/wgengine/wgcfg/mem_ios.go): "iOS has a very restrictive memory limit on network extensions. Reduce the maximum amount of memory that wireguard-go can allocate **to avoid getting killed**" (queues capped at 64). [`netstack_tcpbuf_ios.go`](https://github.com/tailscale/tailscale/blob/main/wgengine/netstack/netstack_tcpbuf_ios.go): buffers left at gVisor defaults "as to not increase pressure towards the NetworkExtension memory limit."
- Tailscale staff confirm the kill behaviour in public: on [#19810](https://github.com/tailscale/tailscale/issues/19810), `nickoneill` (2026-06-23): "speed tests are **known to exceed the system memory limits** when using iOS and an exit node." Reporter's rebuttal: "Wouldn't the right thing to do here be to throttle the speed instead of just allowing the extension to crash?"
- Crash-loop evidence that the extension can die and relaunch repeatedly: [#20963](https://github.com/tailscale/tailscale/issues/20963) (iOS 26.6, TS 1.102.2) — 25 `IPNExtension` crash reports across three boot sessions, "relaunched and crashed approximately every 5–6 seconds", `SIGABRT`, `EXC_BAD_ACCESS at 0x0`.
  - **[INFERENCE]** Your observed 27–33 MB of a 50 MB cap and an unchanged extension pid rules out the OOM/jetsam class and the crash-loop class; it matches the receive-goroutine class (#19504/#15271), where the process is alive and the data plane is dead.
- **Sleep/wake contract.** [`NEProvider.sleep(completionHandler:)`](https://developer.apple.com/documentation/networkextension/neprovider/sleep(completionhandler:)) (iOS 9+): "This method is called by the system when the device is about to go to sleep. `NEProvider` subclasses should override this method if the provider needs to perform any tasks before the device sleeps, such as disconnecting a tunnel connection." [`wake()`](https://developer.apple.com/documentation/networkextension/neprovider/wake()): "called by the system when the device wakes up from sleep mode … such as reconnecting a tunnel connection." **No documented guarantee of promptness or of pairing.**
- [`NETunnelProvider.reasserting`](https://developer.apple.com/documentation/networkextension/netunnelprovider/reasserting): the provider "should set this property to `true` whenever it starts to reconnect to the tunnel server." **[INFERENCE]** an app can observe this via `NEVPNStatus.reasserting` only for VPN configurations *it owns*; it cannot read Tailscale's.
- [`NEPacketTunnelProvider`](https://developer.apple.com/documentation/networkextension/nepackettunnelprovider) requires the `com.apple.developer.networking.networkextension` entitlement, runs at extension point `com.apple.networkextension.packet-tunnel`. [`NEProviderStopReason`](https://developer.apple.com/documentation/networkextension/neproviderstopreason) enumerates why a provider was stopped.
- **API boundary:** there is no public API for one app to restart another vendor's VPN. `NETunnelProviderManager`/`NEVPNManager` manage configurations created by your own app (or by MDM profiles). **[INFERENCE]**, but it follows directly from the entitlement model above and from [#12245](https://github.com/tailscale/tailscale/issues/12245) ("Tailscale for iOS can't connect if there's another VPN configuration") and [#12290](https://github.com/tailscale/tailscale/issues/12290) (profile survives app uninstall).
- I could not retrieve Apple Developer Forums content at scale (the site blocks scripted access behind a human-verification interstitial); one thread I did read, [forums/thread/781522](https://developer.apple.com/forums/thread/781522), is DTS confirming the two-step VPN activation model and that `runningboardd`/`RBSPreventLaunchLimitation` log noise during install is normal, not an extension failure. **No Apple-published rdar/bug acknowledging "utun stuck after handover" was found.**

## 3. App-side networking

- **Apple's own recommendation, [TN3151](https://developer.apple.com/documentation/technotes/tn3151-choosing-the-right-networking-api) (rev. 2026-07-23):** "For WebSocket you have two choices: `URLSession` using `URLSessionWebSocketTask` / Network framework … **Unless you have a specific reason to use `URLSession`, use Network framework for new WebSocket code.**" Also: "The QUIC protocol has significant advantages over TCP. If you're building a custom network protocol, consider using QUIC instead of TCP." And on connect-by-name: the resolve-then-connect anti-pattern "doesn't support on-demand connections, such as **VPN On Demand**" — "even with all of that extra code, your program will still be incompatible with VPN On Demand."
- Network framework now has three API generations: C (`nw_connection_t`), old Swift (`NWConnection`), and **new Swift `NetworkConnection`/`NetworkListener`, introduced 2025 (iOS 26)** — per TN3151's API table.
- [`viabilityUpdateHandler`](https://developer.apple.com/documentation/network/nwconnection/viabilityupdatehandler) (iOS 12+): "A handler that receives updates when data can be sent and received." [`betterPathUpdateHandler`](https://developer.apple.com/documentation/network/nwconnection/betterpathupdatehandler): "Better path events are an indication that a more preferable network path is available. If you can migrate your work to a new connection, try establishing a new connection. Once that new connection is ready, cancel the original connection." — i.e. **Apple gives you the signal, not the migration.** `URLSessionWebSocketTask` exposes neither.
- [`waitsForConnectivity`](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/waitsforconnectivity): "**This property is relevant only during the establishment of a connection.** If a connection is established and then drops, the completion handler or delegate receives an error, such as `NSURLErrorNetworkConnectionLost`." It explicitly names "the device might require a VPN connection but none is available" as a covered case.
- [`allowsConstrainedNetworkAccess`](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/allowsconstrainednetworkaccess) = Low Data Mode; [`allowsExpensiveNetworkAccess`](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/allowsexpensivenetworkaccess) — "iOS 13 considers most cellular networks and personal hotspots expensive"; Apple's tip: "Prefer basing your app's policy logic around the `allowsConstrainedNetworkAccess` property rather than this one." Test via Settings → Developer → Network Override.
- **Multipath TCP:** [`URLSessionConfiguration.multipathServiceType`](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/multipathservicetype-swift.property) (iOS 11+) — "**Multipath TCP requires server support.**" Default `none`; `handover` "provides seamless handover between Wi-Fi and cellular". [`NWParameters.multipathServiceType`](https://developer.apple.com/documentation/network/nwparameters/multipathservicetype-swift.property) (iOS 12+). Requires the [Multipath Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.multipath). **[INFERENCE]** for a Node.js host, MPTCP means a Linux/`mptcp.dev`-capable kernel path in front of the app — not available on macOS hosts, so this is a non-starter for a Mac-hosted server.
- **TCP keepalive is available on `NWConnection`, not on `URLSession`:** [`NWProtocolTCP.Options.enableKeepalive`](https://developer.apple.com/documentation/network/nwprotocoltcp/options/enablekeepalive), [`keepaliveIdle`](https://developer.apple.com/documentation/network/nwprotocoltcp/options/keepaliveidle) ("seconds of idleness that TCP waits before sending keepalive probes"), [`keepaliveInterval`](https://developer.apple.com/documentation/network/nwprotocoltcp/options/keepaliveinterval), [`keepaliveCount`](https://developer.apple.com/documentation/network/nwprotocoltcp/options/keepalivecount) — all iOS 12+. **No equivalent knob exists on `URLSessionConfiguration`** (no such property in the documented API). `URLSessionWebSocketTask` offers only [`sendPing(pongReceiveHandler:)`](https://developer.apple.com/documentation/foundation/urlsessionwebsockettask/sendping(pongreceivehandler:)) — "the task always calls `pongReceiveHandler` in the order it sent the pings" — with no documented timeout, so dead-peer detection is entirely the app's own timer. **[INFERENCE]** on LTE behind CGNAT, a TCP flow whose peer has vanished is indistinguishable from an idle one until your own ping deadline expires; kernel keepalive at any interval above the NAT idle timeout won't save you either.

## 4. Background execution

- [`beginBackgroundTask(expirationHandler:)`](https://developer.apple.com/documentation/uikit/uiapplication/beginbackgroundtask(expirationhandler:)): "Apps running background tasks have a finite amount of time in which to run them … If you don't call `endBackgroundTask(_:)` for each task before time expires, **the system kills the app**." Call it "as early as possible … preferably before your app actually enters the background". Extensions use `ProcessInfo.performExpiringActivity(withReason:using:)` instead. [`backgroundTimeRemaining`](https://developer.apple.com/documentation/uikit/uiapplication/backgroundtimeremaining): "System conditions may end background execution earlier." **Apple does not document a 30-second figure**; the ~30 s number is community-measured, so treat it as unsourced folklore, not a contract.
- [`BGAppRefreshTask`](https://developer.apple.com/documentation/backgroundtasks/bgapprefreshtask) is for "small bits of information"; [`BGProcessingTask`](https://developer.apple.com/documentation/backgroundtasks/bgprocessingtask) runs "only when the device is idle" and "the system terminates any background processing tasks running when the user starts using the device." Neither sustains a socket.
- **APNs push-to-wake** ([Pushing background updates to your app](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app)): "The system treats background notifications as low priority … the system **doesn't guarantee their delivery**. In addition, the system may throttle the delivery … **don't try to send more than two or three per hour.**" Payload `{"aps":{"content-available":1}}`, headers `apns-push-type: background`, `apns-priority: 5`. Delivery may be held: "When the system receives a new background notification, **it discards the older notification and only holds the newest one**"; "If something force quits or kills the app, the system discards the held notification"; "If the user launches the app, the system immediately delivers the held notification."
- Real-world remote-terminal datapoint (user report, tailscale#19504, 2026-07-21): a TestFlight SSH/tmux client "shipped a client change that explicitly closes … SSH connections on backgrounding and backs off reconnects (build 186), **but the failure recurred**", then reduced recurring work further in build 187 — "so this does not appear to be a simple leaked/half-open TCP connection."

## 5. QUIC on iOS, and the Node server side

- [`NWProtocolQUIC`](https://developer.apple.com/documentation/network/nwprotocolquic) — iOS 15 / macOS 12. [`NWProtocolQUIC.Options.idleTimeout`](https://developer.apple.com/documentation/network/nwprotocolquic/options/idletimeout) (ms, iOS 15); [`maxDatagramFrameSize`](https://developer.apple.com/documentation/network/nwprotocolquic/options/maxdatagramframesize) (iOS 16, sets `max_datagram_frame_size`); [`NWMultiplexGroup`](https://developer.apple.com/documentation/network/nwmultiplexgroup) (iOS 15) groups streams on one tunnel. TN3151: Network framework QUIC "supports both QUIC client and QUIC server development", and "**If your ultimate goal is to support HTTP/3, use `URLSession`.** Network framework's QUIC support allows you to create custom network protocols running over QUIC."
- [WWDC21-10094 "Accelerate networking with HTTP/3 and QUIC"](https://developer.apple.com/videos/play/wwdc2021/10094/): "The protocol also supports **connection migration** which allows connections to move seamlessly across different network interfaces without reestablishing a session, for example, between cellular networks and Wi-Fi." This is a statement about **the protocol**, not a claim that Apple's client migrates. The session also notes URLSession has HTTP/3 on by default since iOS 15, discovered via `Alt-Svc` or the DNS `HTTPS` record, with `assumesHTTP3Capable` to skip discovery — "does not guarantee that HTTP/3 will be used. Networks may still block HTTP/3."
- **New in 2026, and materially relevant:** Apple has published a Swift reimplementation of the Network.framework protocol stack — [apple/swift-network-evolution](https://github.com/apple/swift-network-evolution) (created 2026-05-29, pushed 2026-09-09), with [apple/swift-nio-quic](https://github.com/apple/swift-nio-quic), [apple/swift-nio-http3](https://github.com/apple/swift-nio-http3), [apple/swift-tls](https://github.com/apple/swift-tls). All are marked "still in active development and does not offer a stable API yet" / "all types exposed in this package are marked as SPI". The README says it "provides access to the implementations of core networking objects and protocol stack architecture **from Network.framework**".
  - Its `Sources/SwiftNetwork/QUIC/Migration.swift` implements active migration (`migrate(to:connection:)`, path validation via `PATH_CHALLENGE`, `disableActiveMigration()`), but carries live TODOs: `// TODO: Handle preferred address migration`, `// TODO: pending migration feature completion`, `// TODO: pending DCID migration handling`, `// TODO: pending DCID retirement during migration`, `// TODO: pending keepalive loss detection for migration`. **[INFERENCE]** — this is the clearest public evidence that Apple's QUIC migration is real but incomplete as of Sept 2026; it is not proof of what the shipping iOS 26 Network.framework binary does.
- **Multipath QUIC: still a draft.** `draft-ietf-quic-multipath` is at **rev 21, dated 2026-08-13, with no RFC number assigned** ([IETF datatracker](https://datatracker.ietf.org/doc/draft-ietf-quic-multipath/)). No Apple statement of support found.
- **Node.js:** `node:quic` exists in core as [`doc/api/quic.md`](https://github.com/nodejs/node/blob/main/doc/api/quic.md): added **v23.8.0**, **"Stability: 1.0 - Early development"**, and "To access it, start Node.js with the `--experimental-quic` option". It is **not published on nodejs.org/api** (both `quic.html` and `quic.json` return 404, and it is absent from `all.json`) — so it is behind a build flag and effectively unshipped. Current Node is **v26.8.1 (2026-08-26)**. Its docs list RFC 9221 (datagrams) and **RFC 9220 (Bootstrapping WebSockets with HTTP/3)** among target specs.
- **WebTransport on Node:** [`@fails-components/webtransport`](https://www.npmjs.com/package/@fails-components/webtransport) is at **1.6.8, published 2026-09-06**, 59 versions, **~49,700 downloads/week** — actively maintained, "server and client … using libquiche". **There is no Apple WebTransport client API** — no such symbol exists in Network framework or Foundation; **[INFERENCE]** a Swift client would need a third-party stack.

## 6. Cellular NAT

- **The standards floor:** [RFC 4787 REQ-5](https://www.rfc-editor.org/rfc/rfc4787.txt): "A NAT UDP mapping timer **MUST NOT expire in less than two minutes** … A default value of **five minutes or more** … is RECOMMENDED." [RFC 6888 REQ-8](https://www.rfc-editor.org/rfc/rfc6888.txt) (CGN requirements): "Once an external port is deallocated, it SHOULD NOT be reallocated to a new mapping **until at least 120 seconds** have passed."
- **What is actually deployed:** [Tailscale, "How NAT traversal works"](https://tailscale.com/blog/how-nat-traversal-works): "Stateful firewalls have limited memory, meaning that we need periodic communication to keep connections alive. If no packets are seen for a while (**a common value for UDP is 30 seconds**), the firewall forgets about the session." On hard NATs: "Other NAT devices are more difficult, and create a **completely different NAT mapping for every different destination** that you talk to." Tailscale's own published success estimate: "I'd estimate you could get a direct connection **over 90% of the time**, and your relays guarantee *some* connectivity all the time." And: "all connections start out with **DERP preselected**."
- [Tailscale connection types docs](https://tailscale.com/kb/1257/connection-types): "DERP servers are reliable but have limited quality of service characteristics, so they are generally slower than direct connections"; if no direct path and no peer relay, "the devices remain connected using the DERP server."
- **Not found:** published per-carrier UDP binding timeouts, symmetric-NAT prevalence percentages for LTE/5G, or WebRTC TURN-fallback rates from a primary source. The commonly quoted WebRTC "~8–20% need TURN" figure could not be traced to a citable primary source within this session's budget — **do not rely on it.**
- Tailscale itself is uncertain about phone endpoints on cellular: open FR [#6152](https://github.com/tailscale/tailscale/issues/6152) "Stop advertising mobile cellular interface endpoints when on wifi?"

## 7. App Review and depending on a third-party VPN

From the [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) (fetched 2026-09-09):

- **4.2.3(i)** — "**Your app should work on its own without requiring installation of another app to function.**" This is the guideline that bears directly on shipping an app whose only transport is the Tailscale app's tunnel.
- **5.4 VPN Apps** — "Apps offering VPN services must utilize the `NEVPNManager` API and **may only be offered by developers enrolled as an organization**." It also requires an in-app data-collection declaration before purchase/use, forbids selling or disclosing data, and requires a VPN licence in review notes where the territory demands one. Non-compliance means removal from the App Store "and blocked from installing via alternative distribution". **[INFERENCE]** 5.4 governs *offering* VPN services; it does not on its face govern an app that merely runs over someone else's tunnel — but 4.2.3(i) does.
- **4.2.7 Remote Desktop Clients** — directly on point for a phone-controls-my-computer app. If the client "acts as a mirror of specific software or services rather than a generic mirror of the host device": "(a) The app must only connect to a user-owned host device that is a personal computer or dedicated game console owned by the user, and **both the host device and client must be connected on a local and LAN-based network.** (b) Any software or services appearing in the client are fully executed on the host device, rendered on the screen of the host device … (c) All account creation and management must be initiated from the host device … (e) **Thin clients for cloud-based apps are not appropriate for the App Store.**"
- **2.1 App Completeness** — "include demo account info (**and turn on your back-end service!**) if your app includes a login. If you are unable to provide a demo account due to legal or security obligations, you may include a built-in demo mode … with prior approval by Apple. Ensure the demo mode exhibits your app's full features and functionality."
- **2.5.4** — "Multitasking apps may only use background services for their intended purposes: VoIP, audio playback, location, task completion, local notifications, etc."
- **2.5.5** — "Apps must be fully functional on IPv6-only networks."
- Entitlements: [Network Extensions Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.networkextension) and [Multipath Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.multipath) are both Xcode capabilities; the NE one additionally requires enabling on the developer site for Developer-ID macOS distribution.
- **Not found:** any documented App Review rejection specific to "requires a self-hosted server" or "LAN-only". Forums access was blocked, so this is a gap, not a negative finding.
